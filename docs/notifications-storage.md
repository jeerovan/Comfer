# Notification storage boundary

Phase 0 decision, 8 September 2026. This design separates live state, optional retained content and shareable configuration. History capture is not enabled by the cipher prototype.

## Live state and configuration

Live notification text and Android handles remain in memory. Versioned notification configuration is stored separately and contains only settings, package/profile references, schedules and future rule definitions. Configuration writes serialize before IO and publish a new generation only after a successful commit. Invalid configuration preserves the original bytes, exposes recovery and pauses execution.

Configuration exports will be openly readable and unencrypted. They require no password, account, device signature or ownership check. Import validation concerns size, schema and compatibility. Configuration backups and restore journals must exclude live records, retained content, runtime rule IDs, grants and jobs. The current notification schema is not yet integrated into the existing full-app backup manager; phase 8 owns that work.

## Retained content design for phase 5

Use Android Keystore AES-256/GCM keys and authenticated encrypted record blobs. This uses platform cryptography available below the minimum supported API and avoids adding a second cryptography provider. Keys remain in Android Keystore; randomized IVs are generated by the cipher. The record's opaque ID and envelope version are authenticated as associated data. See Android's [Keystore guidance](https://developer.android.com/privacy-and-security/keystore), [recommended cryptography](https://developer.android.com/privacy-and-security/cryptography) and [AES/GCM key-generation example](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec).

`NotificationHistoryCipher` is an executable feasibility boundary, with an isolated-key instrumentation test. It caps plaintext payloads at 16 KiB, bounds encrypted envelopes, rejects altered records/identities and never creates a replacement key when a retained store exists. Test keys are removed afterward. This is not yet a history repository or an automatic key-recovery flow.

The phase-5 repository will use a separate Room database containing encrypted payloads and minimal operational metadata. Keep app identity, title/body and searchable text inside the encrypted payload. Do not create plaintext full-text indexes. Search decrypts bounded batches on a worker dispatcher; measure latency before claiming that 10,000 records are practical. Content exclusions and consent are checked before encryption or persistence. Use opaque IDs for rows; no PendingIntent or raw notification object enters the store.

Enforce age, count, bookmark and physical-storage budgets from AC-05, including database/WAL overhead. Use bounded transactions and maintenance. Key loss, full storage and transaction failure pause capture and dependent saved reminders while leaving the live inbox usable. Keep unreadable data until explicit deletion; do not silently regenerate the key, discard the database or write plaintext. Explicit deletion removes saved data and associated indexes/reminders before removing the key. Hardware-backed key availability and storage-pressure behavior still need physical-device validation.

Uninstall/system restore cannot be treated as a history recovery mechanism. App-level backup is disabled, and explicit system-backup/device-transfer exclusions also cover notification preferences and owned runtime rule IDs. The future explicit configuration exporter must use allowlisted DTOs. Neither ciphertext nor history keys belong in the freely shareable configuration file.
